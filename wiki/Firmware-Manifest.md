# Firmware Manifest — `firmware.json` Reference

Every release publishes two assets: the app image `LucydDeck-firmware-<tag>.bin` and a board-keyed manifest, `firmware.json`. The manifest is the only metadata the LucydDeck app needs to decide whether a release can be installed on a given deck, and to verify the download before it is flashed. Nothing about a release is typed in by hand: [`scripts/firmware_manifest.py`](../scripts/firmware_manifest.py) derives every value from the build, the repository and the image itself, then validates the result against this page before anything is uploaded.

Building a release is a separate walk-through: [Releasing](Releasing).

## 1. Where It Lives

| Fact | Value |
|---|---|
| Release asset name | `firmware.json` |
| Stable release URL | `https://github.com/lucyd-dev/LucydDeck-firmware/releases/latest/download/firmware.json` |
| Image URL | `https://github.com/lucyd-dev/LucydDeck-firmware/releases/latest/download/LucydDeck-firmware-<tag>.bin` |
| Generated by | `scripts/firmware_manifest.py` (`python3 scripts/firmware_manifest.py --bin … --tag …`) |
| Uploaded by | `.github/workflows/release-please.yml` |
| Committed to the repository | never — it is an asset of the release, rebuilt from that release's image |

`latest` is GitHub's newest **stable** release: drafts and pre-releases are never served, so the app needs no channel setting. Both files come from the same `latest/download/` prefix, so the app resolves the asset name against the same release it read the manifest from. There is no GitHub API call anywhere in the path, which means no token and no rate limit.

## 2. Top-Level Fields

The object has exactly these four fields, in this order. Unknown or missing fields are refused before upload.

| Field | Type | Value | Notes |
|---|---|---|---|
| `schemaVersion` | integer | `1` | The only schema the app reads. A different number is refused rather than guessed at. |
| `version` | string | `0.4.0` | Plain `MAJOR.MINOR.PATCH`, no `v`. Equal to `version.txt`, which is also the `vX.Y.Z` the firmware reports as `fw_version`. |
| `releaseUrl` | string | `https://github.com/lucyd-dev/LucydDeck-firmware/releases/tag/v0.4.0` | The page the app links to for "what changed". |
| `boards` | object | one entry per board | Keyed by the board string the firmware reports. See §3 and §7. |

## 3. Board Entry Fields

Each key under `boards` is a board name; each value has exactly these six fields.

| Field | Type | Value | Notes |
|---|---|---|---|
| `asset` | string | `LucydDeck-firmware-v0.4.0.bin` | File name only, no path and no URL. It must be an asset of the same release. |
| `size` | integer | `1174736` | Byte length of the asset. The app compares the downloaded length against it before flashing. |
| `sha256` | string | 64 lowercase hex characters | SHA-256 of the asset. The app hashes the download and refuses a mismatch. |
| `chip` | string | `esp32s3` | The only chip the app flashes. One image, one chip: a release that needs another chip is another entry, not a variant of this one. |
| `address` | integer | `65536` | Flash offset of the app image, `0x10000`. The app refuses any other address, so nothing is ever written outside the app partition. |
| `layout` | string | `max_app_8MB` | The partition layout the image was built for. The app knows this one layout; an unknown layout is refused. |

### `max_app_8MB` and the 8064 KiB limit

`max_app_8MB` is the partition table in `tools/partitions/max_app_8MB.csv`, selected by [`boards/waveshare_esp32s3_touch_lcd_4_3.json`](../boards/waveshare_esp32s3_touch_lcd_4_3.json) (`build.arduino.partitions`):

| Name | Type | Offset | Size |
|---|---|---|---|
| `nvs` | data | `0x9000` | `0x5000` |
| `otadata` | data | `0xE000` | `0x2000` |
| `app0` | app (factory) | `0x10000` | `0x7E0000` |
| `coredump` | data | `0x7F0000` | `0x10000` |

`app0` is `0x7E0000` bytes: 8,257,536 bytes, 8064 KiB. An image of exactly 8,257,536 bytes is accepted; one byte more is refused. There is no OTA slot, so an update is a write to the single factory app — which is why the manifest pins `address` and `layout` instead of trusting the download.

## 4. Worked Example

A published manifest looks like this. `size` and `sha256` differ per build; the rest is fixed for this board.

```json
{
  "schemaVersion": 1,
  "version": "0.4.0",
  "releaseUrl": "https://github.com/lucyd-dev/LucydDeck-firmware/releases/tag/v0.4.0",
  "boards": {
    "WAVESHARE_ESP32_S3_TOUCH_LCD_4_3": {
      "asset": "LucydDeck-firmware-v0.4.0.bin",
      "size": 1174736,
      "sha256": "51957c24c91ece6b2403c6f6ee760e46766db30cc00a318d3799f1c698b0dc7e",
      "chip": "esp32s3",
      "address": 65536,
      "layout": "max_app_8MB"
    }
  }
}
```

## 5. Limits

- **One image, one slot.** The release carries the app image only. The bootloader, partition table, NVS (`0x9000`), `otadata` (`0xE000`), `coredump` (`0x7F0000`) and the SD card are never part of it, and an update never writes them.
- **App slot.** Image size ≤ 8064 KiB (`0x7E0000` bytes).
- **Address.** `65536` exactly. Everything else is refused rather than written to a guessed offset.
- **Chip.** `esp32s3` only.
- **Layout.** `max_app_8MB` only. A release that changes the partition table cannot be installed in-app; it is a BOOT+RESET flash.
- **Boards.** Exactly one entry today, keyed `WAVESHARE_ESP32_S3_TOUCH_LCD_4_3`. A second board ships from its own build and its own manifest entry; the app's lookup by reported board name stays the same.
- **Forward only.** The app installs a manifest `version` that is newer than the running `fw_version`; an equal or older version is not offered.
- **Stable only.** `releases/latest` never serves a draft or a pre-release.
- **Protocol unchanged.** Publishing a manifest does not touch `protocol_version`; it stays `1` until the 1.0.0 release.

## 6. Refusals

### Before publishing — the release workflow

`scripts/firmware_manifest.py` writes the manifest, re-reads it, checks it against §2 and §3, and exits non-zero, failing the release job, on any of these:

| Refusal | Why it matters |
|---|---|
| `version.txt` is not `MAJOR.MINOR.PATCH` | the app compares against `fw_version`, which is built from that file |
| the tag is not `v<version>` | the manifest and the release would name different versions |
| the image is empty, or does not start with the `0xE9` image magic | it is not an application image |
| the image header's chip id is not ESP32-S3 (`9`) | a wrong-chip image would be flashed onto the deck |
| the image is larger than `0x7E0000` bytes | it does not fit `app0` |
| the board's `build.arduino.partitions` is not `max_app_8MB.csv` | `layout` would describe a partition table the build no longer uses |
| `platformio.ini` has no `-D BOARD_NAME="…"` | there is no board key to publish under |
| a field is missing, extra, misnamed or carries a wrong `address`, `layout`, `chip`, `size` or `sha256` | the app would refuse the release after it is public |

### In the app

The app re-checks the same values, first from the manifest and then from the downloaded bytes:

| Condition | Result |
|---|---|
| `boards` has no entry for the deck's reported board | "No firmware published for this deck" — not a generic failure |
| `schemaVersion` is not `1` | the release is refused |
| `chip` or `layout` is not the known value | the release is refused |
| `address` is not `65536` | the release is refused |
| `size` is over 8064 KiB | the release is refused before the deck is asked to reboot |
| the download is shorter, longer or fails | refused, with the next step and a Retry |
| `sha256` does not match the download | refused, with the next step and a Retry |
| `version` is not newer than the installed `fw_version` | no update is offered |

## 7. The Board Key

The key is the board string the firmware reports in `RESP_DEVICE_INFO.board`, which is `BOARD_NAME` from `[common]` in [`platformio.ini`](../platformio.ini):

```
-D BOARD_NAME=\"WAVESHARE_ESP32_S3_TOUCH_LCD_4_3\"
```

The manifest script reads that macro from `platformio.ini`; it never spells the board name itself. A rename in the build flag renames the manifest key in the next release, and the app's lookup — the same string from `CMD_GET_DEVICE_INFO` — keeps working. The string is not a hardware or marketing name: it identifies the build, so it must match exactly, including the underscores and the `4_3` suffix.

## 8. Checking a Release by Hand

Validate the manifest a release published against the image it published:

```bash
curl -fLO https://github.com/lucyd-dev/LucydDeck-firmware/releases/latest/download/firmware.json
curl -fLO https://github.com/lucyd-dev/LucydDeck-firmware/releases/latest/download/LucydDeck-firmware-v0.4.0.bin

python3 scripts/firmware_manifest.py \
  --bin LucydDeck-firmware-v0.4.0.bin \
  --tag v0.4.0 \
  --check firmware.json
```

`--check` compares every field against the image, `platformio.ini` and the tag, and prints the board, size, checksum, chip, address and layout it accepted. It exits non-zero and names the field on a mismatch, so it also works as a post-release smoke test. The version comes from the manifest and the tag from `--tag`; pass `--version` to also require the checked-out `version.txt`.
